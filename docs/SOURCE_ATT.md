# Source Research: AllTheThings (ATT) — Forever Data

Phase 0 research note on the AllTheThings WoW addon as a potential upstream data
source for WoW Forever Atlas, and on "Forever Quest Pins," a downstream addon
that already converts ATT's Forever data. All findings below come from directly
reading the public GitHub repositories (`ATTWoWAddon/AllTheThings` and
`TylerAkins/forever-quest-markers`) via the GitHub API/`gh` CLI on 2026-09-22.
No scraping of the private-server client itself was involved.

Every claim is labeled **CONFIRMED** (directly observed in a fetched file),
**STRONG INFERENCE** (reasonably deduced from confirmed evidence but not
stated outright in a source), or **SPECULATION** (a guess worth flagging but
not backed by direct evidence).

---

## 1. What "Forever" is, according to ATT's own data

**CONFIRMED.** ATT's Parser constants (`.contrib/Parser/lib/Constants/Phases.lua`)
define a dedicated timeline for it:

```
CurrentClassicExpansion.text.en = "Forever"
lore.en = "Forever is a new flavor for World of Warcraft that takes place in
a new world called Azeroth Forever. It features new zones, dungeons, raids,
and a new storyline that continues the story of the original game."

FOREVER_PHASE_ONE  = { readable = "Forever beta - Phase 1", buildVersion = 16001, phaseID = 600,
                        lore.en = "WOW:Forever Beta content 1, available up to level 20." }
FOREVER_PHASE_TWO  = { readable = "Forever beta - Phase 2", buildVersion = 16001, phaseID = 601,
                        lore.en = "WOW:Forever Beta content 2, available up to level 30." }
```

**CONFIRMED.** The addon's `.toc` file (`AllTheThings.toc`) lists `16001` among
its supported `## Interface:` values, alongside standard Retail/Classic/Cata
interface numbers — i.e., ATT treats Forever as a first-class client flavor
with its own interface version, not a reskin of an existing one.

**CONFIRMED.** The build config for Forever data
(`.contrib/.db/forever/.config/forever.config`) declares:
```
"DataPhase": "FOREVER",
"DataPatch": [1, 60, 1, 69893],
"PreProcessorTags": ["ANYCLASSIC","FOREVER","CAMELOT","CLASSIC","CRIEVE",
                       "EXPLORATION","IGNORE_ERRORS","OBJECTIVES","NOSIMPLIFY"]
```
So Forever is currently versioned around client build **1.60.1** (build
numbers seen: 16001 interface / 22248 first-patch build / 69893 or 69913 in
various files — these look like a beta client still in flux). Level cap
content is being rolled out in phases (Phase 1 = level 20, Phase 2 = level 30,
per the lore text above), and the full leveling range configured is 1–60.

**STRONG INFERENCE.** The internal Parser output directory for this data is
named `Camelot`, not `Forever` (see §2) — `CAMELOT` also appears as a
preprocessor tag alongside `FOREVER`. This suggests "Camelot" is ATT's
internal/legacy codename for the same content, now surfaced publicly as
"Forever." (Note the `forever-quest-markers` project's `ATTRIBUTION.md`
independently confirms "Forever" as the public name.)

**Open question about project premise:** the research brief describes Forever
as a "private WoW server." ATT's own source text describes it in
Blizzard-flavor language ("a new flavor for World of Warcraft," its own
Battle.net-style interface/build numbers, "Beta" phases) rather than as an
emulator project. This document does not attempt to resolve that tension —
see **Open Questions** at the end. It matters for the atlas project mainly
insofar as it affects how much the data can be expected to keep changing.

## 2. AllTheThings repo structure

**CONFIRMED.** Repo: `https://github.com/ATTWoWAddon/AllTheThings`, default
branch `master`. Other branches present at research time: `CI-test`,
`annotations`, `change/the_great_static_profession_purge_of_25`,
`filterUpdate`, `providerdb-implementation-wip`, `test-autopluralize`. **There
is no dedicated `forever` branch** — Forever support lives in the mainline
branch as a data phase alongside every other WoW version ATT supports.

Root layout (confirmed via directory listing):
```
AllTheThings.lua / AllTheThings.toc / Bindings.xml / LICENSE / README.md
assets/    lib/    locales/    src/    db/    .contrib/
```

- **`db/<Game>/`** — the *shipped*, built runtime database consumed by the
  live addon at runtime, one folder per supported game flavor:
  `.beta`, `.ptr`, `Camelot`, `Cata`, `Mists`, `Standard`, `TBC`, `Vanilla`,
  `VanillaSOD`, `Wrath`. **`db/Camelot/` is the built Forever database**
  (confirmed by `forever.config`'s `"db-relative": "Camelot/"` setting, see
  above). Each of these folders contains `Categories/*.lua`, `Database.xml`
  (load order), `LocalizationDB.lua`, and `ReferenceDB.lua` (a
  machine-generated aggregate file — its header literally reads *"This file
  is dynamically generated by Parser! DO NOT MODIFY IT MANUALLY!"*).
  `db/Camelot/Categories/` contains: `Character.lua`, `Craftables.lua`,
  `HiddenQuestTriggers.lua`, `Holidays.lua`, `Instances.lua`, `PVP.lua`,
  `Professions.lua`, `Unsorted.lua`, `WorldDrops.lua`, `WorldEvents.lua`,
  `Zones.lua`.

- **`.contrib/.db/forever/`** — the **hand-authored source data** that gets
  compiled (by an internal `Parser.exe` tool, invoked via `build.bat` with
  `config="../.db/forever/.config/forever.config"`) into `db/Camelot/`. This
  is the tree contributors actually edit, and the one worth tracking for our
  importer. Confirmed subfolders: `.config/`, `character/`,
  `dungeons & raids/`, `holidays/`, `pvp/`, `zones/`, `zzOLD/` (deprecated/
  retired entries kept for reference, not built).
  - `zones/kalimdor/` contains per-zone files, e.g. `durotar.lua`,
    `mulgore.lua`, `the barrens.lua`, `teldrassil.lua`, `mount hyjal.lua`,
    `shendralas.lua`, `1 - darnassus.lua`, plus a `.metadata.lua`.
  - `dungeons & raids/` contains Forever-specific instance files:
    `ragefire chasm.lua`, `the stockade.lua`, `shadowfang keep.lua`,
    `1.0 - molten core.lua`, `0.6 - world bosses.lua`,
    `0.5 - dungeon sets.lua`, plus two names **not part of vanilla/classic
    WoW**: `hall of thanes.lua` and `ruins of lordaeron.lua`. This is direct
    evidence of Forever-specific new content (see §4).

- **`.contrib/Parser/`** — the Lua parsing/build tool itself, including
  `lib/Constants/Maps.lua` and `lib/Constants/Phases.lua` (both have `#if
  FOREVER` guarded sections), and `DATAS/00 - Missing DB/00 - Forever/` (a
  todo-list of items/transmog still missing for Forever, e.g. "Lordaeron
  Forever Tabard").

- **`.contrib/.db/shared/constants/`** — cross-version shared constants,
  including `headerIDs.lua` (defines `"World of Warcraft: Forever" = -797`,
  `"World of Warcraft: Forever Collector's Edition" = -794`,
  `"Warcraft Forever Collection" = -795` as category header IDs) and
  `raceIDs.lua` / `Parser Setup Data/FIRST_EXPANSION_PATCH.lua` (which has
  `["FOREVER"] = { 1, 60, 0, 22248 }`, i.e. level range 1–60, phase 0, first
  build 22248).

**CONFIRMED.** Map/zone constants for Forever largely reuse the *same*
`MAP.*` constant IDs as Classic (`.contrib/.db/forever/.config/constants/maps.lua`
defines `MAP.KALIMDOR = 1414`, `MAP.DUROTAR = 1411`, all standard classic
dungeon/raid/zone UiMapIDs), with a `-- #if FOREVER` guarded section in the
Parser's own `lib/Constants/Maps.lua` for anything Forever needs to override
or add. This means: **Forever's zone geography is, for the most part, the
same UiMapID space as vanilla/Classic Era WoW**, with targeted additions.

## 3. Quest, NPC, item, and instance data for Forever

**CONFIRMED** (from reading `.contrib/.db/forever/zones/kalimdor/durotar.lua`
directly). Forever's quest source data is structurally very close to
classic/vanilla ATT quest data, but is a *separately maintained* copy — edits
in Forever's tree do not automatically track Classic Era's tree — and can
diverge. It uses:
- `q(<questID>, {...})` records with fields including `qg` (quest-giver NPC
  ID), `qi` (quest-turn-in item ID), `coord = {x, y, MAP.<ZONE>}`,
  `sourceQuest` / `sourceQuests` (prerequisite quest ID(s)), `altQuests`
  (equivalent/alternate quest IDs, e.g. faction-mirrored variants), `races`
  / `classes` (restrictions), `lvl` (level requirement), and nested `groups`
  for quest objectives/rewards.
- `objective(<index>, {["provider"] = {"i"|"n", id}, ["coord"] = {...}, ["cr"]
  = <creatureID>})` for individual quest objectives (with their own
  coordinates and providing NPC/item/creature).
- `maproot(<parentMapID>, <mapID>, {...})` and `m(<mapID>, {...})` for
  zone/sub-zone containers with `lore`, `icon`, `zone-text-areas`, `groups`.
- `i(<itemID>)`, `recipe(<spellID>)`, `ach(<achievementID>)`, `hqt(<questID>,
  {...})` (hidden quest triggers) as leaf/reward entries.

I did **not** exhaustively diff Forever's quest tree against Classic Era's to
quantify "corrections," but direct evidence of **Forever-specific
divergence** includes:
- Two dungeon files with no classic/vanilla counterpart:
  `hall of thanes.lua`, `ruins of lordaeron.lua` (**CONFIRMED** file
  existence; contents not fully read).
- A `zzOLD/` directory of retired Forever entries distinct from Classic
  Era's own trees, implying independent editorial history.
- Closed PRs/issues tagged for Forever specifically doing data surgery, e.g.
  **CONFIRMED** via GitHub issue/PR search: `#2563 [Forever] Initialize
  ItemDB`, `#2569 [FOREVER] Prune capital cities and Tirisfal Glades`,
  `#2566 [Classic/SoD/Forever] Fixed Nat's Measuring Tape` — all closed,
  indicating active, ongoing Forever-specific corrections distinct from
  Classic Era.

**STRONG INFERENCE.** Because Forever gates content in level-capped betas
(Phase 1 = level 20, Phase 2 = level 30; full range configured to level 60),
the ATT Forever tree is a **moving target under active construction** at
research time, not a finished/stable dataset — corroborated by
`forever-quest-markers`' own README calling itself "Beta" and stating
"Forever's quest data is still moving. Missing or extra pins are often an
upstream ATT gap, not a pin bug."

## 4. "Forever Quest Pins" — relationship to ATT

**CONFIRMED.** Project: `https://github.com/TylerAkins/forever-quest-markers`
(published on CurseForge as "Forever Quest Pins"). It is a WoW Forever addon
(Interface 16001 only) that adds `!` quest-start map pins using data
"automatically generated" from ATT — per its own README and
`ATTRIBUTION.md`.

**How it obtains data (CONFIRMED, not speculation):** It does **not** bundle
ATT, require ATT at runtime, or read ATT's live SavedVariables/addon state.
Instead its maintainer's own tooling (`tools/build_quest_db.py` +
`tools/att_dsl/` — a hand-written Python lexer/preprocessor/parser/evaluator
for ATT's Lua data-definition dialect, plus `emit.py` and `constants.py`)
does an **offline batch conversion**:
1. Clones/reads the ATT git repo (`ATT_REPO_URL =
   "https://github.com/ATTWoWAddon/AllTheThings.git"`) at a pinned commit.
2. Reads only `.contrib/.db/forever/` (the source tree, not the built
   `db/Camelot/` output) — recursively parsing every `.lua` file except
   `.config`/`.wago`/`.git`, with `zzOLD/` (renamed `zzold`) handled/tracked
   separately.
3. Its `att_dsl` package **re-implements enough of Lua** (lexer → parser →
   preprocessor for the `#if FOREVER`-style tags → evaluator) to execute
   ATT's data-definition function calls (`q()`, `m()`, `maproot()`,
   `objective()`, etc.) as plain data without needing an actual Lua runtime.
4. `extract.py` walks the evaluated tree extracting quest records and
   detecting attunement chains (`mark_attunement_chains`); `emit.py` writes
   the final compact Lua tables to `Database/ForeverQuests.lua` and
   `Database/Metadata.lua`.

**CONFIRMED output shape** (`Database/ForeverQuests.lua`, auto-generated,
header states "DO NOT EDIT MANUALLY"):
```lua
ns.Quests = {
  [2] = { mapID=1440, x=75.8, y=69.6, sourceQuests={ 6383 }, faction="Horde", minLevel=20 },
  [16] = { mapID=1429, x=43, y=85.6, qg=255, faction="Alliance", repeatable=true },
  ...
}
```
i.e., ATT's rich nested `groups`/`objective` structures are **flattened** down
to one compact record per quest ID: `mapID`, `x`/`y` (in ATT's/Blizzard's
0–100 `UiMapID` coordinate space — the same system as native world-map pins),
`qg` (quest giver), `sourceQuests` (prerequisites), `altQuests`, `faction`,
`classes`, `minLevel`, `repeatable`. `Database/Metadata.lua` records the exact
upstream ATT commit SHA, quest/coord/attunement counts, and generator
identity for traceability (**CONFIRMED**: `attCommit`, `questCount`,
`coordCount`, `attunementCount`, `filesParsed` fields present).

Per the addon's own README (v0.1.24-era, at research time): "ships 3505
quests with 3729 coordinate pins across 49 maps." Reputation-gate
restrictions are extracted and stored but **not yet used** for pin filtering
(explicitly noted as a beta limitation). Item-started quests without a map
coordinate are omitted from pins. Patrol NPCs use ATT's static points plus a
heuristic second point.

**Answer to "fork or consume":** it **consumes and converts**, it does not
fork ATT's codebase, and it does not bundle ATT at runtime. The generated
database is a one-way, point-in-time derivative snapshot re-built
periodically against a pinned ATT commit.

## 5. Licensing and redistribution terms

**CONFIRMED.** `ATTWoWAddon/AllTheThings`'s repo-wide `LICENSE` file
(and GitHub's own license detection) is the **MIT License**:
> "Copyright (c) 2026 AllTheThings WoW Addon... Permission is hereby granted,
> free of charge, to any person obtaining a copy of this software and
> associated documentation files (the "Software"), to deal in the Software
> without restriction, including... to use, copy, modify, merge, publish,
> distribute, sublicense, and/or sell copies of the Software... The above
> copyright notice and this permission notice shall be included in all
> copies or substantial portions of the Software."

This is a single blanket license covering the whole repository — code and
`db`/`.contrib` data files alike; ATT's README does not carve out a separate,
more restrictive license for its data tables. **There is no separate
"content license" that would forbid extraction.**

**STRONG INFERENCE / practical reading for our project:** MIT permits
extracting, transforming, and redistributing ATT's quest/NPC/coordinate data
into a new database — including inside a differently-licensed project —
*provided* the MIT copyright notice and permission text is preserved
somewhere in that derivative's distribution (typically satisfied by an
`ATTRIBUTION`/`THIRD_PARTY_NOTICES` file, exactly as `forever-quest-markers`
does it). MIT does **not** require the derivative itself to be MIT-licensed,
and does not require external "source IDs" (ATT's internal questIDs, NPC
IDs, etc.) to be treated as anything other than raw facts we can re-key —
those numeric IDs are themselves Blizzard's game data (quest/NPC/item IDs),
not ATT's original expression, so there's no copyright concern in re-using
the *numbers* regardless of license; the license question is really about
ATT's curated *structure/text/organization* (descriptions, lore text,
curated coordinate corrections, category groupings), which we would still
need to attribute if reused verbatim.

**Directly modeled precedent:** `forever-quest-markers` is GPLv3 for its own
code but explicitly keeps the *converted* ATT-derived data files under a
separate MIT notice in its `ATTRIBUTION.md`, and states outright: "This
repository does not claim ownership of ATT data." This is a workable template
for WoW Forever Atlas: dual-track licensing where our own importer/normalizer
code can carry whatever license we choose, while ATT-derived raw fields
retain an MIT attribution note pointing back to ATT.

**Not found / not confirmed:** No explicit ATT statement (README, wiki, or
CONTRIBUTING doc) directly addresses third-party redistribution of *bulk
extracted data into another database/product* beyond the license text
itself — i.e., there's no FAQ entry saying "yes, you may build a website with
our data." The permission is inferred from the license grant, not from an
explicit blessing. Given MIT's broad language this is a low-risk inference,
but it is still an inference, not a quoted permission.

## 6. Data file formats (for importer design)

**CONFIRMED.** ATT's Forever source data (`.contrib/.db/forever/**/*.lua`) is
plain **Lua source**, executed by ATT's own internal Parser tool at build
time (not by the WoW client), organized as nested function calls that build
up a tree, e.g. (illustrative fragment, not reproduced at length):
```lua
maproot(MAP.KALIMDOR, MAP.DUROTAR, {
  groups = { m(VALLEY_OF_TRIALS, {
    groups = { n(QUESTS, {
      q(794, { qg = 3145, coord = {42.8, 69.0, MAP.DUROTAR},
               sourceQuests = {792, 1499}, races = HORDE_ONLY,
               groups = { objective(1, { provider = {"i", 4859}, ... }) } }),
    }) },
  }) },
})
```
Key constructor functions relevant to an importer: `maproot`/`m` (map/zone
containers with `lore`, `icon`, `zone-text-areas`), `n` (named group
headers), `q` (quest, with `qg`/`qi`/`coord`/`sourceQuest(s)`/`altQuests`/
`races`/`classes`/`lvl`/nested `groups`), `objective` (quest step with its own
`coord`/`provider`/`cr`), `i` (item), `recipe`, `ach` (achievement), `hqt`
(hidden quest trigger). Preprocessor directives like `-- #if FOREVER` /
`-- #endif` gate version-specific blocks, resolved by ATT's own Parser
before the file becomes part of the shipped `db/Camelot/*.lua` output.

The **shipped runtime** files (`db/Camelot/ReferenceDB.lua` etc.) are instead
machine-minified single-line Lua tables/closures (marked "DO NOT MODIFY
MANUALLY") — not meant for hand parsing, and not the layer worth targeting;
the human-authored `.contrib/.db/forever/` tree is the right target if we
ever wanted to parse ATT source directly ourselves.

**CONFIRMED — a viable, already-proven alternative:** rather than writing our
own Lua-DSL parser, `forever-quest-markers`'s `tools/att_dsl/` package
(`lexer.py`, `parser.py`, `preprocessor.py`, `evaluator.py`, `extract.py`,
`emit.py`, `constants.py`) is a working, from-scratch Python implementation
of exactly this: a minimal Lua lexer/parser sufficient to evaluate ATT's
constructor-call data files without a real Lua interpreter. This is
independent proof that ATT's dialect is regular enough to parse externally,
and a template worth studying (not copying verbatim, given its GPLv3
license) if WoW Forever Atlas's importer needs to consume ATT-shaped Lua
directly rather than someone else's pre-converted output.

## 7. Implications for WoW Forever Atlas's pipeline

- Two possible upstream layers exist: (a) ATT's raw `.contrib/.db/forever/`
  Lua source (richest, but requires a Lua-DSL parser — an already-proven
  approach per §6), or (b) `forever-quest-markers`'s pre-flattened
  `Database/ForeverQuests.lua`/`Metadata.lua` (simpler to parse, but lossy —
  no zone lore/icons, no full objective chains, no items/achievements, and
  reputation gates are present but described as inert).
- Per the project's own stated principle, **external IDs (ATT questIDs,
  Blizzard NPC/item/map IDs) must never become our primary keys** — this
  research doesn't change that; it only confirms those numeric IDs are
  Blizzard's underlying game data anyway (not ATT's copyrightable
  expression), so re-keying them into our own canonical IDs during
  Normalization/Entity Matching is both required by our own architecture and
  uncomplicated licensing-wise.
- If ATT is used as a source, our importer should record the upstream ATT
  commit SHA per import (mirroring `Metadata.lua`'s `attCommit` field) for
  reproducibility and to support attribution.
- Attribution obligations under MIT are modest but real: we should carry an
  ATTRIBUTION/THIRD_PARTY_NOTICES entry crediting ATT (copyright + license
  text) if any of its curated data or text is imported, matching the pattern
  `forever-quest-markers` already uses successfully.

## Open Questions

1. **Is "WoW Forever" actually a private/emulated server, or a Blizzard
   beta/experimental flavor?** ATT's own source text describes it in
   official-sounding terms ("a new flavor for World of Warcraft," Battle.net
   interface/build numbers, "Beta Phase 1/2"). This document takes no
   position; it matters for licensing risk assessment (Blizzard's ToS/EULA
   posture toward third-party data reuse could differ from a private-server
   community's norms) and should be resolved before Phase 1 data-sourcing
   decisions.
2. **How stable is the Forever dataset right now?** Both ATT and Forever
   Quest Pins describe it as actively moving beta content (level-capped
   phases, "upstream ATT gap" caveats). We should decide whether to pin to a
   specific ATT commit/tag per import or track a moving target, and how
   often to re-sync.
3. **Full ATT vs. Classic Era diff not performed.** I confirmed several
   Forever-specific corrections (closed PRs, unique dungeon files, a
   separate `zzOLD` tree) but did not do a systematic file-by-file diff
   against ATT's `Standard`/`Vanilla` trees to quantify how much Forever
   data has actually diverged vs. simply been copied. Worth a dedicated
   Phase 1 spike if the exact scope of divergence matters for scoping our
   Normalization layer.
4. **No direct contact/permission from ATT maintainers.** MIT's grant
   appears sufficient on its own, but if this project intends heavy, ongoing
   bulk ingestion of ATT's Forever tree, it may still be worth a courtesy
   heads-up to the ATT team (Discord linked from their README) — not a legal
   requirement, purely a community-relations judgment call.
5. **`forever-quest-markers`'s own att_dsl parser is GPLv3-licensed.** We can
   study its architecture but should write our own implementation rather
   than copy its code if our importer needs to end up under a different
   license.
6. Did not verify whether ATT's Forever data is fetched from a `wago-directories`
   external source (`.wago` folder referenced in `forever.config`) that might
   carry its own terms distinct from the MIT-licensed repo — the `.wago`
   subfolder contents were not inspected in this pass.
